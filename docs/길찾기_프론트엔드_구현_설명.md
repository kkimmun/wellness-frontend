# 길찾기 프론트엔드 구현 설명

## 1. 구현 목적

지도 화면에서 사용자가 출발지와 도착지를 선택하고 이동 수단별 경로를 조회할 수 있도록 구현했다.

지원 범위는 다음과 같다.

- DB에 저장된 장소를 출발지 또는 도착지로 선택
- 브라우저가 제공한 현재 위치 좌표를 출발지 또는 도착지로 선택
- 자동차, 대중교통, 자전거, 도보 경로 조회
- 도보 경로에서 DB 장소 경유지 1~3개 선택
- 입력한 경유지 순서를 유지한 경로 요청
- 조회한 경로 목록 표시 및 선택
- 선택한 경로를 카카오 지도 위에 선으로 표시
- Oracle `PLACE` 테이블의 삭제되지 않은 장소를 지도 핀으로 표시
- 대중교통 경로의 승차·하차 장소, 버스/지하철 노선, 이동 방향과 정류장 순서 표시
- 환승 도보와 출발지에서 첫 승차지, 마지막 하차지에서 목적지까지의 연결 도보 표시

## 2. 구현 파일 구조

```text
src/
├─ api/
│  └─ route.js
└─ features/map/
   ├─ MapPage.jsx
   └─ components/
      ├─ RoutePanel.jsx
      ├─ RoutePanel.styles.js
      ├─ TransitRouteDetails.jsx
      ├─ TransitRouteDetails.styles.js
      ├─ SearchPanel.jsx
      ├─ DetailPanel.jsx
      └─ BasicInfoTab.jsx
```

새 파일은 `RoutePanel.jsx`, `RoutePanel.styles.js`, `TransitRouteDetails.jsx`, `TransitRouteDetails.styles.js`, `route.js`다. 나머지 네 파일은 기존 화면과 길찾기를 연결하기 위해 수정했다.

## 3. 핵심 기술

### 3.1 React 컴포넌트와 상태 관리

#### 무슨 기술인가?

React의 함수 컴포넌트와 `useState`, `useEffect`, `useRef`, `useMemo`를 이용해 화면 상태와 사용자 동작을 관리하는 방식이다.

#### 왜 사용했는가?

출발지, 도착지, 경유지, 이동 수단, 검색 결과, 선택 경로처럼 서로 연관된 화면 상태가 많다. 이 상태를 `RoutePanel` 안에서 관리하고, 지도에 필요한 선택 경로만 `MapPage`로 전달하면 역할을 분리할 수 있다.

#### 어떻게 사용했는가?

- `RoutePanel`: 입력, 검색, 요청, 결과 상태 관리
- `MapPage`: 패널 열림 여부와 지도에 표시할 선택 경로 관리
- `useRef`: 요청 취소용 `AbortController`와 카카오 지도 인스턴스 보관
- `useMemo`: URL의 `placeNo`와 핀 목록으로 현재 상세 장소 계산

```jsx
const [transportType, setTransportType] = useState("CAR");
const [routeData, setRouteData] = useState(null);
const [selectedRoute, setSelectedRoute] = useState(null);
```

### 3.2 Axios API 모듈과 AbortController

#### 무슨 기술인가?

Axios는 백엔드 HTTP API를 호출하는 라이브러리다. `AbortController`는 새 검색이나 새 길찾기 요청이 시작될 때 이전 요청을 취소할 수 있는 브라우저 표준 기능이다.

#### 왜 사용했는가?

프로젝트가 이미 `src/api/axios.js`에서 공통 URL, 쿠키, 응답 처리를 관리하고 있으므로 같은 구조를 재사용했다. 빠르게 검색어를 바꾸거나 화면을 닫았을 때 이전 응답이 최신 화면을 덮어쓰지 않도록 요청 취소도 적용했다.

#### 어떻게 사용했는가?

`src/api/route.js`에 다음 두 요청을 분리했다.

```text
GET /api/routes/origins?query=장릉
GET /api/routes?...길찾기 파라미터...
```

컴포넌트가 사라질 때 남은 요청도 취소한다.

```jsx
useEffect(
  () => () => {
    searchControllerRef.current?.abort();
    routeControllerRef.current?.abort();
  },
  [],
);
```

### 3.3 URLSearchParams 반복 파라미터

#### 무슨 기술인가?

객체 값을 URL 쿼리 문자열로 변환하는 브라우저 표준 API다.

#### 왜 사용했는가?

도보 경유지는 백엔드가 아래와 같은 반복 파라미터 형식으로 받는다.

```text
waypointPlaceNos=15&waypointPlaceNos=16&waypointPlaceNos=20
```

`waypointPlaceNos[0]`처럼 대괄호가 포함된 형식은 요청 URL 오류 또는 바인딩 오류를 만들 수 있으므로 사용하지 않았다.

#### 어떻게 사용했는가?

`src/api/route.js`의 `serializeRouteParams`가 배열 값을 같은 키로 순서대로 `append`한다. 따라서 화면에서 입력한 경유지 순서가 백엔드 요청에도 그대로 유지된다.

### 3.4 react-kakao-maps-sdk Polyline과 LatLngBounds

#### 무슨 기술인가?

카카오 지도 SDK를 React 컴포넌트 방식으로 사용하는 라이브러리다. `Polyline`은 좌표 목록을 지도 위 선으로 표시하고, `LatLngBounds`는 전체 좌표가 화면에 들어오도록 지도 범위를 계산한다.

#### 왜 사용했는가?

백엔드 길찾기 응답의 `path`를 실제 지도 경로로 보여줘야 하며, 경로 선택 후 사용자가 지도를 직접 확대·축소하지 않아도 전체 경로가 보여야 한다.

#### 어떻게 사용했는가?

백엔드 좌표를 다음과 같이 변환한다.

```text
X_AXIS = 경도 = Kakao lng
Y_AXIS = 위도 = Kakao lat
```

```jsx
<Polyline
  path={selectedMapPath}
  strokeWeight={7}
  strokeColor="#2196F3"
/>
```

길찾기 패널의 폭을 고려해 지도 왼쪽 여백을 크게 잡은 뒤 `setBounds`를 호출한다.

### 3.5 Browser Geolocation API

#### 무슨 기술인가?

브라우저가 사용자 동의를 받은 뒤 현재 기기의 위도와 경도를 제공하는 기능이다.

#### 왜 사용했는가?

현재 위치는 DB 장소 번호가 없으므로 `startPlaceNo` 또는 `endPlaceNo` 대신 좌표로 길찾기를 요청해야 한다.

#### 어떻게 사용했는가?

현재 위치를 선택하면 다음처럼 요청값을 만든다.

```text
출발지: startX=longitude, startY=latitude
도착지: endX=longitude, endY=latitude
```

브라우저가 위치 권한을 거부하면 사용자에게 권한 확인 메시지를 표시한다.

### 3.6 styled-components

#### 무슨 기술인가?

JavaScript 파일에서 컴포넌트 단위 CSS를 작성하는 CSS-in-JS 라이브러리다.

#### 왜 사용했는가?

기존 프로젝트가 `styled-components`와 `theme.js`를 사용하고 있으므로 동일한 코드 형식과 디자인 값을 유지하기 위해 사용했다.

#### 어떻게 사용했는가?

길찾기 전용 스타일은 `RoutePanel.styles.js`와 `TransitRouteDetails.styles.js`에 작성했다. 공통 `theme.js`, `GlobalStyles.js`, 공통 버튼 파일은 변경하지 않았다.

### 3.7 구조화된 대중교통 단계와 연결 도보 조회

#### 무슨 기술인가?

백엔드가 반환한 대중교통 `steps` 배열을 순서대로 타임라인에 표시하고, 대중교통 API가 제공하지 않은 출발·도착 연결 도보만 기존 도보 길찾기 API로 추가 조회하는 방식이다.

#### 왜 사용했는가?

대중교통 요약 시간과 거리만으로는 사용자가 어디에서 몇 번 버스를 타고, 어느 역에서 환승하고, 하차 후 목적지까지 어떻게 걸어야 하는지 알 수 없다. 또한 카카오 응답의 `guidance` 문장을 프론트에서 다시 분석하면 문장 형식 변경에 취약하므로 백엔드가 구조화한 값을 그대로 사용한다.

#### 어떻게 사용했는가?

백엔드는 각 단계에 다음 값을 내려준다.

```text
type, vehicleNames, vehicleTypes, boardingPlace, alightingPlace,
direction, stopCount, transfer, stopNames, guidance, distance, time, path
```

`TransitRouteDetails.jsx`는 배열 순서를 바꾸지 않고 버스·지하철·환승 도보를 표시한다. 선택한 대중교통 경로의 처음과 끝이 도보 단계가 아니고 실제 좌표가 30m 이상 떨어진 경우에만 아래 도보 요청을 보낸다.

```text
출발지 → 첫 승차지: transportType=WALK&routeOption=SHORTEST
마지막 하차지 → 목적지: transportType=WALK&routeOption=SHORTEST
```

두 연결 경로는 `Promise.allSettled`로 처리한다. 한 구간 조회가 실패해도 대중교통 본 경로는 계속 보여주며, 실패한 도보 구간만 안내 메시지로 표시한다. 조회된 연결 도보의 `path`는 대중교통 `path` 앞뒤에 붙여 지도에도 함께 표시한다.

### 3.8 DB 기반 지도 핀 조회

#### 무슨 기술인가?

MyBatis로 Oracle `PLACE`, `TYPE_DETAIL`, `TYPE` 테이블을 조회하고, 공개 지도 핀 API를 통해 React 지도 화면에 전달하는 방식이다.

#### 왜 사용했는가?

기존 프론트는 `/api/places/pins` 요청이 실패하면 `mapPinsMockData`를 표시했다. 백엔드에는 해당 URL이 없었기 때문에 실제 실행에서는 항상 가짜 장소가 나타났다. DB를 단일 데이터 기준으로 사용하면 관리자 화면에서 장소가 추가·삭제된 결과가 지도에도 일치한다.

#### 어떻게 사용했는가?

```text
GET /api/places/pins
```

백엔드는 `DEL_YN = 'N'`인 장소만 `PLACE_NO` 순서로 반환한다. 응답에는 장소 번호·이름·설명·주소·전화번호·분류·조회수와 DB 좌표가 포함된다.

```text
xAxis = DB X_AXIS = 경도 = Kakao lng
yAxis = DB Y_AXIS = 위도 = Kakao lat
```

프론트는 API 실패 시 목업 장소로 대체하지 않는다. 핀 목록을 비우고 DB 장소 조회 실패 메시지를 표시하므로 서버 오류가 가짜 정상 화면으로 숨겨지지 않는다. DB API에 없는 평점·리뷰·운영시간·이미지도 임의 값으로 채우지 않는다.

### 3.9 교통수단별 지도 경로 색상

#### 무슨 기술인가?

대중교통 경로의 `steps[].path`를 하나의 선으로 합치지 않고 이동 단계별 `Polyline`으로 표시하는 방식이다. `type`, `vehicleTypes`, `vehicleNames`를 이용해 각 구간의 교통수단과 노선을 판별한다.

#### 왜 사용했는가?

전체 경로를 파란색 한 줄로 표시하면 도보 구간과 승차 구간, 환승 지점을 지도에서 구분하기 어렵다. 국내에서 익숙한 버스 색상 체계를 적용하면 별도의 학습 없이도 이동수단을 빠르게 판단할 수 있다. 서울시 공식 버스 안내의 간선 파랑, 지선·마을 초록, 광역 빨강 체계를 기준으로 사용했다.

참고: [서울시 시내버스 노선체계](https://news.seoul.go.kr/traffic/archives/1706)

#### 어떻게 사용했는가?

| 구간 | 지도 표현 | 분류 기준 |
|---|---|---|
| 도보 | 회색 `#6B7280` 점선 | `WALKING` 또는 연결 도보 |
| 시내·마을버스 | 초록 `#2E8B57` 실선 | 마을, 지선, 순환, 시내 |
| 일반·간선버스 | 파랑 `#1565C0` 실선 | 일반, 간선, 좌석 및 분류되지 않은 버스 |
| 광역·직행버스 | 빨강 `#D32F2F` 실선 | 광역, 직행, 급행, 공항, M버스 |
| 지하철 | 각 노선 고유색 실선 | `vehicleNames`의 호선명 |

지하철은 1~9호선, 김포골드라인, 공항철도, 신분당선 등 알려진 노선색을 사용하고 알 수 없는 노선만 보라색으로 표시한다. 지도 오른쪽 아래 범례와 상세 경로 아이콘에도 같은 색을 사용한다.

## 4. API 요청 규칙

### 4.1 DB 장소 출발·도착

```text
GET /api/routes?startPlaceNo=248&endPlaceNo=7&transportType=CAR&routeOption=MIN_DISTANCE
```

### 4.2 현재 위치 좌표 출발

```text
GET /api/routes?startX=126.8027&startY=37.5586&endPlaceNo=7&transportType=WALK&routeOption=SHORTEST
```

### 4.3 순서가 있는 도보 경유지

```text
GET /api/routes?startPlaceNo=248&endPlaceNo=7&transportType=WALK&routeOption=SHORTEST&waypointPlaceNos=15&waypointPlaceNos=16&waypointPlaceNos=20
```

경유지는 도보에서만 표시하며 최대 3개다. 출발지, 경유지, 도착지 사이에 같은 DB 장소나 같은 좌표가 중복되면 프론트에서 요청 전에 차단한다.

### 4.4 대중교통

```text
GET /api/routes?startPlaceNo=248&endPlaceNo=7&transportType=PUBLIC_TRANSIT&transitType=BUS_AND_SUBWAY&sortType=MIN_TIME
```

대중교통 결과는 백엔드가 정렬한 순서를 그대로 표시한다. 프론트에서 교통수단별로 다시 묶거나 재정렬하지 않는다.

대중교통 결과 카드를 선택하면 `steps`가 다음 순서로 펼쳐진다.

```text
출발지 연결 도보 → 승차/하차 구간 → 환승 도보 → 다음 승차/하차 구간 → 목적지 연결 도보
```

## 5. 기존 파일 수정 내역

기존 코드에서 수정한 부분에는 `길찾기 기능 연동:` 또는 `기존 코드 개선:` 주석을 남겼다.

| 기존 파일 | 수정 위치 | 수정 내용 | 수정 이유 |
|---|---|---|---|
| `src/features/map/MapPage.jsx` | import, 상태, 지도 렌더링, 검색·상세 연결부 | `RoutePanel`, `Polyline`, 경로 좌표 변환, 경로 범위 조정 추가 | 길찾기 패널과 지도 경로를 연결하기 위해 |
| `src/features/map/MapPage.jsx` | 상세 장소 계산 effect | 중복 state를 제거하고 URL `placeNo`로 `selectedPlace` 계산 | React Hook 검사 오류와 중복 상태 불일치를 방지하기 위해 |
| `src/features/map/components/SearchPanel.jsx` | props, 출발·도착 버튼 | 임시 `alert`를 `onSetOrigin`, `onSetDestination` 호출로 교체 | 검색 장소를 실제 길찾기 입력으로 전달하기 위해 |
| `src/features/map/components/SearchPanel.jsx` | 검색 함수와 IntersectionObserver | `useCallback` 의존성 및 observer 정리 대상 고정 | 변경 파일의 Hook 규칙을 지키고 오래된 참조를 방지하기 위해 |
| `src/features/map/components/DetailPanel.jsx` | props와 `BasicInfoTab` 호출 | `onFindRoute` 전달 | 상세 패널의 경로찾기 버튼을 상위 지도 상태와 연결하기 위해 |
| `src/features/map/components/BasicInfoTab.jsx` | 경로찾기 버튼 | 현재 장소를 `onFindRoute`로 전달 | 선택 장소를 도착지로 설정하기 위해 |

이번 대중교통 상세 개선에서 수정한 기존 길찾기 파일에도 `대중교통 상세 안내:` 주석을 남겼다.

## 6. 화면 사용 방법

1. 지도 장소를 검색하거나 마커를 선택한다.
2. 장소 카드의 `출발` 또는 `도착` 버튼을 누른다.
3. 반대편 장소명을 입력하고 Enter를 누른다.
4. 반드시 백엔드 검색 결과 목록에서 장소를 선택한다.
5. 이동 수단과 옵션을 선택한다.
6. 도보인 경우 필요에 따라 경유지를 최대 3개까지 입력하고 검색 결과에서 선택한다.
7. `경로 찾기`를 누른다.
8. 결과 카드를 누르면 해당 경로가 지도에 표시된다.
9. 대중교통 결과 카드를 누르면 승차·하차·환승·도보 안내가 이동 순서대로 펼쳐진다.

현재 위치 버튼은 출발지와 도착지 입력란 오른쪽의 위치 아이콘이다.

## 7. 실행 설정

로컬 환경 파일에는 다음 값이 필요하다. 실제 키는 Git에 올리지 않는다.

```text
VITE_API_URL=http://localhost:8080/api
VITE_KAKAO_MAP_KEY=카카오_JavaScript_키
```

카카오 REST API 키는 백엔드가 관리하며 프론트엔드가 전달하지 않는다. 프론트엔드는 지도 화면 표시를 위한 카카오 JavaScript 키만 사용한다.

## 9. 위험도 평가

### 🟡 브라우저 위치 권한

사용자가 권한을 거부하거나 HTTP 환경에서 브라우저 정책이 위치 조회를 제한하면 현재 위치 기능을 사용할 수 없다. DB 장소 검색은 계속 사용할 수 있으며, 화면에 권한 확인 메시지를 표시한다.

### 🟡 외부 API 및 백엔드 상태 의존

길찾기 결과는 백엔드와 카카오 API 상태에 의존한다. 오류가 발생하면 mock 경로로 대체하지 않고 백엔드 오류 메시지를 표시해 잘못된 경로를 정상 결과처럼 보여주지 않는다.

### 🟡 번들 크기 경고

프로덕션 빌드는 성공했지만 Vite가 500kB를 넘는 JavaScript 청크 경고를 표시한다. 이 경고는 실행 실패가 아니며, 향후 화면 단위 동적 import를 적용하면 초기 로딩 크기를 줄일 수 있다. 이번 길찾기 범위에서는 라우팅 구조를 넓게 변경하지 않았다.

### 🟢 공통 스타일 영향

길찾기 스타일을 기능 전용 파일에 격리했고 공통 테마와 전역 스타일을 수정하지 않아 다른 화면에 미치는 스타일 위험은 낮다.
